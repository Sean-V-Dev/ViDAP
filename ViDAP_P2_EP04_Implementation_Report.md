## 3. D2.4 — Attempt and provenance record

`run_attempt` in `python/src/vidap_execution/run.py:132` calls accepted `plan_execution` once and the dispatcher's same whole-table preflight before allocation. Preparation, binding, planning, scalar-policy, seed, missing-lock, and runtime-table failures remain pre-dispatch refusals; Phase 1 ordered diagnostics are not remapped. After preflight it allocates a canonical lowercase UUIDv4, publishes pending ownership, then calls the EP03 dispatcher once. A UUID collision refuses without overwriting the existing directory. An initial ownership-publication error returns an in-memory failed record without calling a handler; a terminal-publication error returns a failed outcome with explicit pending/cleanup state.

The durable schema is `vidap.run-record/1.0` in the fixed `vidap.attempt-ownership/1.0` envelope. It records attempt ID; workflow ID, semantic digest and contract snapshot reference; plan, binding and runtime-table revisions; schedule-ordered node ID, operation key, binding revision, resolved scalar parameters, ordered input content references and status; explicit seed or null; bounded environment; UTC start/end and elapsed milliseconds; attempted/completed/failed/blocked/unrelated identities; outcome; computed/reused events; sanitized diagnostics; publication state; and owned relative artifact references. `AttemptRecord` recursively freezes all nested maps and sequences (`run.py:43`–`58`). Failed-node outputs have no computed event or published output reference. Completed prior work remains visible on a failed attempt but the outcome is failed.

Persisted parameters and seed are limited to null, booleans, signed 64-bit integers and finite IEEE-754 numbers (`run.py:65`–`73`, `run.py:147`–`154`). Strings, collections, paths, secrets, non-finite numbers, oversized integers and arbitrary objects refuse before durable write. This EP04 restriction does not alter Phase 1 workflow validity. The fingerprint (`run.py:75`–`93`) is derived internally from Python implementation/version, OS family/architecture, and SHA-256 of both fixed lock files. Missing or unreadable locks refuse; callers cannot supply the fingerprint. Host/user names, environment variables, process IDs, absolute paths, package dumps and raw incoming values are absent. Absence of seed is null, distinct from zero. The test handlers do not use seed.

## 4. D2.5 — Owned local artifacts

`python/src/vidap_execution/artifacts.py:14`–`18` fixes the ignored checkout-local root `.vidap-local/runs/`, canonical UUIDv4 directory names, `record.json` and optional synthetic `proof-output.bin` slots, with fixed same-directory staging names. The JSON record is UTF-8, validated and capped at 256 KiB; opaque proof bytes are capped at 64 KiB. The code publishes a pending ownership record before handlers or proof writes, then atomically replaces only that attempt's pending `record.json` with `succeeded` or `failed`. EP04 does not retain dispatch outputs by default. The proof slot is a test-only opaque ownership challenge, not a product output format.

Path checks reject symlink/reparse managed components, non-directory roots, noncanonical IDs, and resolved escape from the fixed checkout root. Fixed staging uses exclusive creation; first pending and proof publication use same-directory `os.rename` on Windows so an existing target cannot be overwritten, while terminal publication uses `os.replace` only after pending ownership is read under pinned directory handles (`artifacts.py:138`–`229`). A failed terminal publication leaves an in-memory failed result; rollback verifies pending ownership and removes only unpublished proof/staging slots while the same run directory is pinned (`artifacts.py:248`). An inability to complete rollback is reported as incomplete cleanup. Pending state is never interpreted as success.

The shared `_pinned_attempt` guard (`artifacts.py:351`) pins the checkout, managed root, runs root, and target directory with Windows handles before any owned slot publication, proof write, rollback, or removal. Its share modes deny concurrent delete/rename sharing while ownership and fixed entries are checked and changed. The managed descendants are opened without reparse traversal and verified as non-reparse directories by handle. The fixed OneDrive checkout root is pinned as the already-resolved source checkout. For initial allocation, `_create_pinned_directory` (`artifacts.py:291`) uses Windows `NtCreateFile` with `FILE_CREATE` and `FILE_DIRECTORY_FILE`, relative to the already pinned runs-root handle. Creation and acquisition of the new directory handle are one operation: refusal before creation leaves no UUID directory; a subsequent pre-publication check failure disposes of the new directory through its original handle. A failed first pending write uses the same handle disposition (`artifacts.py:170`). Windows refuses disposition if the directory is nonempty. Neither cleanup path follows a later directory lookup. `remove_attempt` (`artifacts.py:416`) still verifies ownership format, ID, fixed recorded slots, state, references, entry types and absence of unexpected entries/links. Its target handle, not a later path lookup, is marked for deletion with `FileDispositionInfo` (`artifacts.py:408`) after the verified slots are removed. It never recursively deletes a run or purges by age. The Windows mechanism follows [Microsoft's `NtCreateFile` creation contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile), [`CreateFileW` share-mode contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), and [`SetFileInformationByHandle` disposition contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle).

Focused tests exercise pending-to-terminal publication, proof bytes, size/format refusals, collision, stage cleanup after partial write, unexpected-entry deletion refusal, another run's survival, and Windows reparse-attribute refusal. The new parametrized regression (`test_execution_artifacts.py:100`) forces refusal during atomic directory creation and immediately after creation during the next check. Both cases leave no UUID directory and preserve a separate attempt. The removal regression (`test_execution_artifacts.py:218`) and three parametrized publication, rollback, and proof-write regressions (`test_execution_artifacts.py:253`) attempt a no-symlink-privilege directory swap immediately after ownership read. The pinned directory blocks the first rename; both attempts retain their original records, the second attempt's proof bytes remain intact, and no spare directory is left.
